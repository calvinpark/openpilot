# TSK Manager

## Background

comma.ai makes DIY ADAS devices — currently the comma threeX (C3X / tizi) and comma four (C4 / mici). Toyota added cryptographic SecOC signatures to CAN messages, blocking comma from writing to the bus.

Willem (ex-comma) found a way to pull the SecOC key from the EPS firmware on 2021–23 RAV4 Prime; the same hack works on 2021–23 Sienna Hybrid, and with modifications on Yaris. TSKM is Calvin's GUI around Willem's method. Background in `/Users/calvin/GitRepos/docs/README.md`.

Calvin's cars: 2023 Sienna Hybrid (C3X), 2023 Bolt EV 2LT (C4). Both devices validate against the Sienna.

## Architecture

The `tskm` branch, based on `commaai/nightly-dev`, is a local phone-first web app on port `11111`. It replaced the RayLib GUI, whose final release is frozen at `tskm-0.11.0`. The web app was developed on a `tskmloop` branch, since folded into `tskm` and deleted.

### Boot Flow

`launch_chffrplus.sh` on device boot:

1. Creates `/cache/tsk` **and `/cache/params`** and chowns both to comma — the server runs as comma but `/cache` is root-owned, so the dirs it writes to must exist first: `/cache/tsk` for dumps and the oracle, `/cache/params` for the installed `SecOCKey`. Recreated each boot; `/cache` clears on AGNOS update.
2. Runs `python3 tsk/prefetch.py` — standalone RayLib GUI that clones the recommended/alternate openpilot branches. Blocks until done.
3. Starts `tsk.web.server` in the background, *before* the manager, so it survives the pipeline's `pkill manager.py`.
4. Starts the openpilot manager (`./manager.py`) from the nested `openpilot/` tree.
5. UI at `http://<device-ip>:11111`.

`/data/openpilot` (the `tskm` checkout) is a **wrapper**: `tsk/` (this app) plus a nested `openpilot/` (a full bundled openpilot the device drives with). Installing `recommended`/`alternate` `rmtree`s + `move`s `/data/openpilot`, replacing the wrapper with a plain openpilot; `RebootManager.execute()` kills the manager first (`_stop_manager()`) so it isn't running from the tree being moved. "Install a different fork/branch" deletes `/data/continue.sh` (the AGNOS boot pointer, `cd /data/openpilot && exec ./launch_openpilot.sh`), dropping the device to the comma installer.

### File Layout

- `tsk/prefetch.py` — standalone RayLib prefetch GUI (not manager-managed). Detects C3X vs C4 screen size.
- `tsk/lib/` — all TSKM behavior; shared logic lives here.
  - `env.py` — paths, branch constants, device detection: `is_agnos`, `CACHE_DIR` (`/cache` on device, `~/comma_data/cache` off), `DATAFLASH_DIR`, `DATAFLASH_PAYLOAD_PATH`, `CAN_MESSAGES_DIR`, `CAN_ORACLE_PATH`, and the recommended (`commaai/nightly-dev`) / alternate (`sunnypilot/staging`) install targets.
  - `extractor.py` — legacy single-step extraction (Willem). `hack()` uploads `payload.bin`, dumps RAM `0xFEBE6E34–0xFEBE6FF4`, parses KEY_4. `_connect_panda()` stashes the handle; `_close_panda()` releases it from the server's `finally`. pandad flashes the panda firmware on boot, so there's no flash call here.
  - `dump_dataflash.py` — DataFlash dump (the 2021+ path). `dump(progress_cb)` uploads `payload_dataflash_ff200000_ff208000.bin` and dumps `0xFF200000–0xFF208000` (32 KB), returning `{status, frames, bytes, total, dump_path, message}`. `_finalize()` (pure, off-device testable) classifies the outcome:
    - **complete** — full 32768 bytes; writes `dump_ff200000_ff208000.bin`.
    - **partial** — the key window `KNOWN_KEY_OFFSET` (0x6e14) is captured but not the full range; writes the `.partial` sidecar Find can use.
    - **key_missed** — the key window wasn't captured (one frame or nearly all of it); writes nothing, asks for a re-dump.

    `_finalize()` returns the three statuses above; the server's job thread sets `failed` on an unhandled exception. `is_agnos`-gated. Shares the UDS session preamble with `extractor.py` by deliberate duplication (distinct payload, range, and parser, kept independently testable).
  - `collect_can.py` — CAN oracle capture. `collect(progress_cb)` records sync (0x0F) + protected (0x2E4/0x131/0x344) frames on buses 0/2 in READY Mode until both targets are met (sync is the bottleneck; protected floods), capped at 60 s; writes `can_oracle.ndjson`; returns `{status, sync, protected, ...}` (complete | insufficient; the server sets `failed` on an unhandled exception). `count_oracle_frames()` tallies a persisted oracle, skipping malformed lines. `is_agnos`-gated.
  - `matcher.py` — key finder. `run()` reads the oracle + the dump (complete file, else the `.partial` sidecar, setting `dump_partial`) and calls `find_key()`: exhaustive stride-1 scan over every window, 5-sample sync union first pass, accept at ≥ `MATCH_FLOOR` (30) matches with ≥ 2 sync. Hand-rolled RFC-4493 AES-CMAC that computes the same 28-bit SecOC MAC as opendbc `secoc.py` (opendbc uses the pycryptodome `CMAC` library; the MAC values match, the code is a reimplementation). Pure computation; returns the key, does not install it.
  - `dump_range.py` — **`dump` branch only, not on `tskm`.** Exploratory range dumps over six fixed EPS ranges beyond the production DataFlash window. Each range is a separate 4096-byte payload with the range baked into four 16-bit shellcode immediates, so a profile is just `(payload, start, end, sha256)`. Keys and ranges: `codeflash` `0x00000000-0x00200000`, `extended_codeflash` `0x01000000-0x0100C000`, `local_ram_pe1` `0xFEBE0000-0xFEC00000`, `local_ram_self` `0xFEDE0000-0xFEE00000`, `global_ram` `0xFEEF8000-0xFEF08000`, `dataflash` `0xFF200000-0xFF210000`. Every range sits inside one 16 MB top-byte window, which the frame reassembly requires (only the low 24 bits ride in a frame). `IDLE_TIMEOUT` 10 s is what normally ends a run, since the EPS stops emitting once it walks off the end of its range; `MAX_SECONDS` 1500 s is the per-run ceiling. Complete dumps are `dump_<key>_<start>_<end>_<stamp>.bin`, gapped ones `partial_..._NofM.bin`, so a glob can never mix the two. `is_agnos`-gated.
  - `preflight_store.py` — persistent state behind preflight, and the only module the gate needs: `security_access_log.json` (`record_security_access_attempt()`, `has_unlocked()`, `is_unlock_blocked()`, `block_reason()`, `read_security_access_log()`, `classify_security_exception()`), the measured route (`save_route()`, `route_for()`, `identity_for()`, `has_run()`), and the saved reports (`save_report()`, `list_reports()`, `latest_report()`, `report_stamp()`, ordered newest-first on the stamp rather than the filename). Imports only `env`, touches no panda, so it is entirely testable off-device. It exists apart from `preflight.py` because the three dumpers need the gate while `preflight.py` imports `dump_range` — one module would be an import cycle.
  - `preflight.py` — the one-press probe: panda, a DEFAULT-session bus sweep over buses 0/1/2 under elm327 param 0 **and** 1, identity DIDs, a 3-second per-bus traffic tally, a **route probe** on every answering pair, then **one** `dump_range.dump()` on the `dataflash` profile, which is the whole exploit and therefore at most one `SEND_KEY`. `render_screenshot()`, `result_line()`, `_answering_pairs()`, `_select_route()` and `_fold_stages()` are pure. Analyses no dumped byte. `is_agnos`-gated with `run_mock()`, whose mock is a **two-route car** so the laptop pass exercises the probe loop.

    **`_probe_route()` is what picks the route.** Per answering `(bus, param)`: DEFAULT, EXTENDED, the four services `PROBE_SERVICES` (`0x11`, `0x28`, `0x34`, `0x85`) as bare service bytes, a `0xF186` read, EXTENDED again, PROGRAMMING, then DEFAULT to leave the ECU clean. Same 0.1 timeout and 0.5/0.7 settles the dumpers use, so a PROGRAMMING answer the exploit would catch is not missed by a stricter probe. `_select_route()` takes the first pair that opened PROGRAMMING; when none did, **the exploit step is skipped entirely** and no key goes out. A `(0, 0)` that answers is probed first and short-circuits the loop on success, so 74 runs of proven Sienna behaviour cost no extra car time.

    The four services are the 2026-07-25 silent class, and that sweep ran on param 0, the OBD-II multiplexed path. Sending them on every answering route turns each silence into a comparison, which is what settles open item 0. The `0xF186` read doubles as the liveness marker and the session-lapse detector: `EXPECTED_LIVENESS` is `"03"` (EXTENDED_DIAGNOSTIC), and anything else earns a line in the block because it makes that route's silences unattributable.
  - `dump_files.py` — file operations over the whole `/cache/tsk` tree: `list_files()`, `arcname()`, `zip_name()`, `delete_all()`. Exists so `server.py` stays HTTP routing: the server owns the transport (streaming the archive into the socket) and its own in-memory state reset, and nothing else there touches the filesystem. Scope is the tree rather than any one producer, which is why it is separate from `preflight_store.py`. Cannot reach the installed key: that is `/cache/params/SecOCKey`, a sibling of the tree.
  - `key_file_manager.py` — key read/write/delete, `format_key()`.
  - `reboot_manager.py` — reboot/install actions with key-status prompts.
  - `payload.bin` — legacy extraction payload.
  - `payload_dataflash_ff200000_ff208000.bin` — DataFlash dump payload (SHA256 `d48988366b…a06e34`, verified before use; byte-identical to Willem's I-CAN-hack/secoc `while-loop` branch).
  - `payload_{codeflash,extended_codeflash,local_ram_pe1,local_ram_self,global_ram,dataflash}_*.bin` — the six range payloads (`dump` only). Generated by `Sienna2024Comma/notes/tools/make_payloads.py`, which pins their SHA256 in `SHIPPED_SHA256` and asserts in `--diff` mode that each differs from the proven `dataflash` one only at the four range patch sites.
- `tsk/web/` — HTTP + static UI only.
  - `server.py` — Python stdlib `ThreadingHTTPServer` on `11111`.
  - `static/index.html` — phone-first main page (iOS Settings design).
  - `static/extractor.html` — legacy TSK Extractor page (dark terminal, auto-runs on load).
  - `static/can-collector.html` — CAN page; POSTs to start the real job, polls `/api/can-status`. Short-circuits a complete oracle, attaches to a running one, retries after insufficient/failed.
  - `static/dataflash-collector.html` — DataFlash page; same pattern against `/api/dataflash-status`.
  - `static/range-collector.html` — range-dump page (`dump` only); takes `?profile=<key>` and runs that one profile against `/api/range-status?profile=<key>`. **Runs on entry, no button**, and refuses to start when preflight has not run or the ECU is blocked.
  - `static/preflight.html` — preflight page (`dump` only): pinned screenshot block, live log, copy-as-text. No owner controls beyond Run preflight.

`tsk/common`, `tsk/c3`, `tsk/c4` should not exist on `tskm`. They are the RayLib layout, preserved at `tskm-0.11.0`.

### Web Server

Binds `0.0.0.0:11111`. Serves frozen assets from `tsk/web/static`. Writes the device URL into `Offroad_NoFirmware` (via the background `offroad_alert_loop`) so the comma screen shows it — rewritten when the URL changes or the file is gone, since the manager wipes it on start.

API endpoints:

- `/api/health` (GET) — server info, dry_run flag, detected addresses.
- `/api/status` (GET) — key install status via `RebootManager.key_status_payload()`.
- `/api/reboot` (GET/POST) — GET lists reboot actions, POST executes one.
- `/api/extract` (POST) — legacy single-step extraction. Off-AGNOS dry run cycles 3 scenarios.
- `/api/uninstall` (POST) — removes the installed key via `KeyFileManager`.
- `/api/can-status` (GET) — `{ready, status, sync_count, protected_count, seconds, message}` from `can_state`. `ready == (status == "complete")`.
- `/api/can-collect` (POST) — starts the background collect job, returns immediately. 409 if a panda op is already running. Off-AGNOS: mock ramp.
- `/api/dataflash-status` (GET) — `{ready, status, frames, bytes, total, message, size}` from `df_state`. `partial` is a key-region-covered dump Find accepts; `key_missed` writes no file (re-dump).
- `/api/dataflash-dump` (POST) — starts the background dump job, returns immediately. 409 if a dump is in progress. Off-AGNOS: `dump()` raises `NotAGNOSError` and the job falls back to a mock ramp.
- `/api/match` (POST) — runs `matcher.run()`; on `found` installs the key via `KeyFileManager` and returns it with a screenshot message (modal title "Success!"), for a complete or partial recovery alike. Otherwise returns status + counts + debug fields (`windows_scanned`, `survivors`, best-candidate `address`, `dump_partial`) for the not-found modal. 500 with traceback on unhandled exception. 409 if a match is already running.
- `/api/range-dump` (POST) — **`dump` only.** Starts one range-dump profile named by `{"profile": "<key>"}`; 400 on an unknown key, 409 if another panda op is running. Off-AGNOS: mock ramp.
- `/api/range-status` (GET) — **`dump` only.** With `?profile=<key>`, that profile's live state; with no query, `{"profiles": [...]}` for every profile, which is what the index rows poll.
- `/api/preflight` (POST) — **`dump` only.** Starts the background preflight job; 409 if a panda op is already running. Off-AGNOS: `run_mock()`.
- `/api/preflight-status` (GET) — **`dump` only.** `{status, has_run, blocked, passed, result, route, log, report, screenshot, message, bytes, total}`. `passed`, `has_run` and `blocked` are recomputed from disk on every call, so a rejected key recorded by a dump job gates the UI on the next poll rather than after a restart. **`passed` is the gate**, and it is `result == "ready to dump"`; `has_run` only says a route was stored, which a run that never opened PROGRAMMING also does.
- `/api/download-dumps` (GET) — **`dump` only.** Streams all of `/cache/tsk` as `tsk_dumps_<ecu serial>_<stamp>.zip`, dongle id when no serial was read. No Content-Length; the client reads to close. 404 when the tree is empty, 409 while a panda job runs.
- `/api/delete-dumps` (POST) — **`dump` only.** Removes everything under `/cache/tsk`, log included, and resets the CAN, DataFlash, range and preflight states. Never touches `/cache/params/SecOCKey`, which is outside that tree. **Three outcomes, kept distinct:** 409 while a panda job runs, 500 when files remain on disk afterwards ("Some files could not be removed"), 200 otherwise. `delete_dumps()` returns a reason token rather than a bool so waiting is only ever suggested for the one cause waiting fixes.
- `/api/clear-cache` (POST) — `clear_can()` deletes the CAN oracle file and `clear_dataflash()` deletes the dump + `.partial` (each also resets its in-memory state). 409 while a dump/collect runs. Does not touch the key, and does not touch range dumps.

CAN and DataFlash run as real background jobs: `can_state`/`can_lock` and `df_state`/`df_lock` hold live progress; threads run `collect()` / `dump()`, set `status="failed"` on any unhandled exception, and `start_*_job()` reject a concurrent start. A single `panda_lock` serializes extract/dump/collect over the one physical panda — held for the whole operation and released in the job's `finally`, which also calls `TSKExtractor._close_panda()`. `rehydrate_can_state()` and `rehydrate_dataflash_state()` run in `main()` so persisted CAN/dump data shows as done after a restart.

### Hard Rules

`tsk/web/server.py` is HTTP routing only. Do not add key paths, key validation, key read/write, device detection, extractor wrappers, or reboot file ops. **Filesystem work over the dump tree is included**: `tsk/lib/dump_files.py` owns enumeration, archive naming and deletion, and the server keeps only the transport and its own in-memory state. If behavior exists in `tsk/lib`, call it; if it doesn't, add it to `tsk/lib` or ask first. Do not invent alternate key storage — use `KeyFileManager`.

What the server legitimately still owns: the locks and the `*_state` dicts (they are per-process, not persisted), the job threads, and writing the archive bytes into the socket.

### Storage

- Frozen code: `/data/openpilot/tsk`
- CAN oracle: `/cache/tsk/can-messages/can_oracle.ndjson`
- DataFlash dumps: `/cache/tsk/dataflash/` — `dump_ff200000_ff208000.bin` (exactly 32768 bytes; the matcher prefers it) or a `.partial` sidecar (key window captured, full range not)
- Range dumps (`dump` only): `/cache/tsk/range-dumps/` — timestamped `dump_*`/`partial_*` files that accumulate; kept out of the DataFlash dir so the matcher never sees them
- Preflight (`dump` only): `/cache/tsk/preflight/` — one `preflight_<ecu serial>_<stamp>.json` per run plus `route.json`, the measured `(bus, param)` with the panda and harness it was measured on
- Security access log (`dump` only): `/cache/tsk/security_access_log.json`
- Prefetched repos: `/data/tsk-recommended`, `/data/tsk-alternate`

All of `/cache` survives reboot and clears on AGNOS update.

**Everything above under `/cache/tsk` is what Download dumps zips and Delete dumps removes**, so one archive carries the CAN oracle, every dump, every preflight report and the security-access log together. The installed key is at `/cache/params/SecOCKey`, a **sibling** of that tree rather than inside it, which is what makes Delete dumps safe by construction rather than by a check.

### Method & Design Notes

Durable rationale for why the pipeline is shaped this way:

- **Car-agnostic — no model gate.** Any car the owner picks may run. The verifier is the safety net: a wrong car either fails security access (EPS not in the Willem family) or nothing verifies. A wrong 16-byte window clears a 28-bit sync MAC at 2⁻²⁸; with ≥ 2 sync samples a false install is 2⁻⁵⁶ — no bad install is possible. The only car-specific constant is `KNOWN_KEY_OFFSET = 0x6e14`, used only to classify a partial as usable vs `key_missed`.
- **No candidate system.** Exhaustive stride-1 scan over every window (~32,753), one AES-CMAC each, sub-second — no entropy filtering, scoring, or caps. Survivors (expect 0–1) get full sync + protected verification. Acceptance is an absolute floor (`MATCH_FLOOR` 30, ≥ 2 sync), not a percentage: a wrong window reaching 30 is ~2⁻⁶⁶⁰.
- **Three failure modes, kept distinct.** (1) Security access denied → EPS not in the exploit family. (2) Dump completes, nothing verifies → exploit works but the key isn't in `0xFF200000–0xFF208000` for this EPS. (3) Verify passes → key extracted.
- **Key delivery.** `KeyFileManager` writes `/cache/params/SecOCKey` + Params `SecOCKey`; `card.py` reads both, gated on `CP.secOcRequired`, surviving the install `move`/reboot/AGNOS. Cars past their last-supported year need SunnyPilot with manual year selection (e.g. 2024 Sienna → pick 2023).
- **Cold dumps often come back `partial`/`key_missed`; the variable is not the car.** The EPS is ruled out categorically: it's a state machine, so after `bl_reset` it returns to the same state and can't be the run-to-run difference. The lost data is a fixed-size (124-byte), moving, single-burst gap during the 8192-frame flood — dropped on the RX/USB path, so by elimination the variable is host/panda-side; which specific state (USB enumeration, RX FIFO, flash-on-boot settle) is unresolved, and "warm-up" is a placeholder for it, not a mechanism. Behavioral remedy (Calvin, in-car): keep the comma powered so the panda doesn't cold-cycle between car power cycles, and the first dump on entering Not Ready is complete every time. Bk2ol's "prime the EPS" and a throwaway retry both worked only by incidentally reaching that warm state — the EPS was never primed. Production keeps the dump as-is; a stuck user's fix is keeping the comma powered, and most Sienna partials still capture the key regardless.
- **Extraction (RAM) vs dump (DataFlash).** The legacy extraction reads a firmware-specific RAM copy at `0xFEBE6E34` (per-car; fails the KEY_4 checksum on Yaris — "needs modifications"). The dump reads persistent DataFlash at `0xFF206E14`, whose layout is shared across these EPS variants — so it generalizes where the RAM extraction needs per-car addresses.
- **DataFlash size.** The production dump window is 32 KB. Every key seen is inside it (Sienna/Yaris `0x6e14`; a `0x6410` candidate on the 2024-Sienna profile), so production stays at 32 KB. The wider payloads now exist and have run (`dump`, `dump_range.py`): on `R7F701381` the array reads as 64 KB of content with `0xFF210000-0xFF238000` a single repeated value, which is why the `dataflash` profile stops at `0xFF210000`. The part number question is answered for the Sienna family (`R7F701381`, self-named at code-flash `0x000180`) and open for the Corolla family (`R7F701383`, no public datasheet), where a larger array would put the key outside every window the tool reads.
- **A dump is not a measurement until it repeats.** Two DataFlash captures 21 seconds apart, both reporting 100 % coverage, differed in 16,703 of 65,536 bytes (25.487 %). Nothing about a region should be claimed from one image, and a null from one image is the weakest result the tool produces.

Direct server test:

```
python3 -m tsk.web.server
```

The server needs the project venv for `Crypto` (`matcher.py` imports it at module level): `.venv/bin/python -m tsk.web.server`. A bare `python3` fails at import.

Off-AGNOS: `/api/extract` dry-run cycles 3 scenarios (fake-key success, short error, long error with traceback). `dump()` / `collect()` raise `NotAGNOSError`, so the background jobs fall back to a **server-side mock ramp**; the collector pages poll the real status endpoints either way. Preflight instead has its own `run_mock()` in `tsk/lib`, which drives the same report shape through the same `render_screenshot()` as the real run, so the block, the result line, the JSON write and both UI gates are exercised on a laptop.

`tsk/lib/preflight_store.py` imports only `env`, so its whole surface — the blocking rule, the route invalidation, the report round-trip — runs under a bare `python3` with no venv and no opendbc. The gate itself needs both: `PYTHONPATH=$PWD/opendbc_repo .venv/bin/python`.

**Any off-device test that resets state must run under an isolated `HOME`.** `env.py` derives `COMMA_DATA_DIR` from `os.path.expanduser("~")` with no override, so a suite that clears `CACHE_DIR/tsk` wipes the tree a dev server on the same machine is serving. `HOME=<scratch> python3 test_x.py` gives it a private cache. This has destroyed a live session once.

**And every such suite refuses to run on a comma.** Each opens with `if is_agnos(): sys.exit(...)`, because on a device the same `TSK_DIR` resolves to `/cache/tsk` and one run would take an owner's dumps, CAN oracle, preflight reports and security-access log together. The isolated `HOME` depends on remembering a prefix; the guard does not.

**A second dev server needs a port override, since `PORT` is a module constant.** `import tsk.web.server as server; server.PORT = 11112; server.main()` in a three-line driver, run under its own `HOME`, gives a full second instance to click through without disturbing the one already on `11111`. That is how the 2026-08-20 revision was checked live while a session was open on the old code.

## Preflight, built 2026-08-19 on `dump`

Built and mock-tested; **never run in a car.** Supersedes the 2026-08-18 spec, which was written in a design session without the tree open: every one of its statements about code was a hypothesis, and six turned out wrong under review.

**Why.** Every failure on an unknown car currently produces the same thing, an empty dump or a timeout, with no way for the owner to tell which cause they hit. One button that runs the chain in order and prints a report makes each cause a distinguishable line, and the report is the artifact owners send Calvin.

**Scope rule (Calvin, 2026-08-19): preflight runs the exploit and dumps, and analyses no dumped byte.** Content gets examined offline from the downloaded files. Dropped with that rule: the `mcu_part` read at `0x180`, `secret_slots_as_expected`, the `0xBFD8`/`0xBFE8` comparisons and the per-address `capture_quality`, and therefore the `identify` payload and its `make_payloads.py` edit. Nothing in `Sienna2024Comma` changes.

### Steps

One press, no confirmation taps. Each step records `ok`, an NRC, or `silent`, so a run that dies partway ships everything above it. Steps that never ran print `not attempted`.

1. Panda: `get_serial()`, firmware, `car_harness_status` from `health()`.
2. Bus sweep: DEFAULT session at `0x7a1` on buses 0, 1 and 2 under **both** `param=0` and `param=1`, recording which answered under each. A DEFAULT session is the question that changes nothing whether it is answered or refused, so this step only narrows the field.
3. Identity: `0xF181`, `0xF18C`, `0xF186`, on the first answering pair. Free reads, no security, no state change. **Ahead of the probe**, so the part number and the serial survive a run that ends there; Span's failed run on 2026-08-19 produced both and they were the most useful thing it carried.
4. Traffic: per-bus frame counts, distinct arbitration IDs, `0x0F` sync counts. Reported only; a zero sync count never gates the outcome, since albinoelephant's 1,232 sync rows sit on buses 0 and 2 with zero on bus 1. Before the probe as well as before the exploit, since both flood the bus.
5. Route probe, on **every** pair the sweep found answering: DEFAULT, EXTENDED, the four services `0x11`/`0x28`/`0x34`/`0x85` as bare service bytes, a `0xF186` read, EXTENDED again, PROGRAMMING, then DEFAULT to leave the ECU clean. The route that opens PROGRAMMING is the route the exploit runs on. A `(0, 0)` that answers is probed first and short-circuits on success.
6. The exploit run: **one** call to `dump_range.dump()` on the existing `dataflash` profile (`payload_dataflash_ff200000_ff210000.bin`, `0xFF200000-0xFF210000`, already pinned, already run on the Sienna and the Corolla), on the route step 5 chose. That single call performs the session ladder, one `REQUEST_SEED`, one `SEND_KEY`, the upload, the trigger and the collect, so one press sends at most one unlock. **When no route opened PROGRAMMING the step is skipped entirely**: no route could have run it, and skipping sends no key and hands the car back sooner. Zero frames fails, any frames passes, and a gapped read never moves the outcome. The bytes go to disk for offline examination.

**Why PROGRAMMING chooses (Calvin, 2026-08-20).** The first cut picked the route by array order over the answering pairs, and on Span's Corolla both `(1, 0)` and `(1, 1)` answered, so the exploit went down `param=0`, the OBD-II multiplexed path the 2026-08-11 finding says confounds every silent result. The dual sweep measured that `param=1` works and the tool then ignored it, which cost the session. A DEFAULT session answers on any route that reaches the ECU at all; PROGRAMMING is the only transition that has ever told two paths apart on that car.

**Why those four services.** They are the 2026-07-25 silent class, the four that produced total silence while thirteen others answered with data or a precise NRC. That sweep ran on `param=0`, so each silence measures the gateway as much as the ECU. Sending the same four on every answering route turns each one into a comparison, which is what settles Corolla open item 0 whatever the outcome. They are safe as bare service bytes for the reason the 07-25 standing rule gives: a service byte with no sub-function has to be rejected on length, so the ECU answers without acting, and all four were already sent to this EPS in July with nothing happening. They go out **in EXTENDED, ahead of the PROGRAMMING attempt**, so a bare `0x11` is never sitting in a session where a reset could take.

**Why EXTENDED is re-sent before PROGRAMMING.** The 2026-07-24 `preamble_probe` defect: stacked timeouts pushed PROGRAMMING more than six seconds past the EXTENDED request with no tester-present, and that run's own NRCs show it went out from a lapsed session. The `0xF186` read is both the liveness marker, so a silence above it is attributable to the route rather than to an EPS that dropped out, and the lapse detector, since it returns the active session byte. `EXPECTED_LIVENESS` is `"03"`; anything else earns a line in the screenshot block.

The 2026-08-18 shape had a separate security stage followed by a dump that repeats the whole flow at `dump_range.py:370-386`, so one press sent two keys while the report claimed one. Collapsing them is what keeps the count truthful. The report still prints DEFAULT, EXTENDED, PROGRAMMING, seed, unlock and dump as separate lines, because the single `except` over the four session transitions at `dump_range.py:378` is split per transition and the security `except` at `:387` is split per NRC. Same sequence, same sleeps; only exception granularity changes.

### Route: measured, never mapped

The dumpers use the `(bus, param)` pair whose probe opened PROGRAMMING, stored with the report and cleared when `get_serial()` or `car_harness_status` differs from what the report recorded. When no route opened PROGRAMMING the first answering pair is stored instead, which keeps the security-access log keyed to this car; the dump rows gate on the report's result, so storing a route enables nothing on its own.

**Hard correction, 2026-08-19: "stock" does not name a bus.** The bus is a function of three variables, the car's connector family, the owner's rewiring, and the elm327 param, and `panda/board/boards/red.h` combines two of them in one exclusive-or, `(mode == CAN_MODE_NORMAL) != (harness.status == HARNESS_STATUS_FLIPPED)`. Measured:

```
family                 pins      param   EPS answers on   evidence
Sienna / RAV4 Prime    stock     0       bus 0            74 runs
Corolla (Toyota-B)     stock     0       bus 1 via OBD    span, several sessions
Corolla (Toyota-B)     stock     1       bus 1 harness    span, 2026-08-19
Corolla (Toyota-B)     swapped   0       bus 0            albinoelephant, 15 files
```

**The `param=1` row was measured on 2026-08-19** and it answered a DEFAULT session, which is the first `param=1` data on any car in this project. Whether PROGRAMMING answers there is still unmeasured: that run's exploit went down `param=0` because the route was picked by array order, which is the defect the probe replaced.

"Stock" appears twice with two different answers, so any mapping from the label to a bus has picked one row and generalised it. Which row a session picks follows which half of the record it read first: the Sienna material is 74 successful runs that never mention the harness, the Corolla material is entirely bus 1 and pin swaps. Three sessions have written that mapping wrong in opposite directions. Measuring the pair removes the mapping entirely.

Compounding the confusion, "harness" names the comma adapter, the car's wiring and the panda's `car_harness_status` field, while "swap" names the owner's repin, the panda's flip detection and the elm327 param. Six referents, two words.

**And the tool no longer asks or guesses (Calvin, 2026-08-20).** "Swapped" means the CAN conductors differ from that car's factory pinout, so detecting it needs the factory pinout as a baseline, and a car-agnostic tool has none for a car nobody has measured. `car_harness_status` cannot supply it either: `panda/board/drivers/harness.h:52-87` samples only the SBU1 and SBU2 ADC voltages and reports `FLIPPED` when `sbu1 < sbu2`, so it reads the plug's orientation and never touches the pins a repin moves. Span's stock-pinned Corolla read `harness flipped` and the page printed `Detected` under **Swapped**. Inferring the pin state from `app_sw_id` plus the answering bus was proposed and rejected the same day: that is a model gate, and it answers `unknown` on exactly the car the tool exists for. The pin state is therefore **not collected at all**. A repin is already visible as a different answering pair, which the sweep records as a measurement, and albinoelephant's repinned Corolla produced 15 dumps through stock `dump_range.py` with no label anywhere in the loop.

### `security_access_log.json`

Under `/cache/tsk/`. Records **every** unlock attempt, accepted or rejected, keyed by the ECU serial from `0xF18C`, with an `unattributed` entry alongside for a car whose `0xF18C` does not answer. Each attempt records the timestamp, the outcome, the `service_id`, the `error_code` when there is one, which of the two security calls raised it, and the caller. Functions `record_security_access_attempt()`, `has_unlocked()`, `is_unlock_blocked()`, `read_security_access_log()`.

**Blocked when the serial has no accepted attempt and carries a `NegativeResponseError` from the `SEND_KEY` call with `error_code` in `{0x35, 0x36}`.** Those two are the ECU's own verdict on a key it received and judged. Everything else is recorded and blocks nothing: any failure of the `REQUEST_SEED` call, since no key was sent; any timeout or invalid-response error, since nothing came back to attribute; and any other `error_code`, including `0x37`, which `opendbc_repo/opendbc/car/uds.py:285` gives as "required time delay not expired", a timing state whose preceding `0x36` already blocks.

Timeouts stay out of the blocking set deliberately. A timeout is silence, covering both "the key never reached the ECU" and "it arrived and the answer was lost", and only the second advanced anything. If a timeout did hide a delivered bad key, the ECU's counter is armed and the next attempt returns `0x35` or `0x36`, which blocks. Blocking on silence instead converts a documented routine event, the EPS dropping out under load, into a dead end on a car's first press.

**Once any attempt on a serial is `accepted`, nothing gates from any path** (Calvin, 2026-08-19: the car is known to work, so later failures are glitches owners retry). A block therefore exists only before the first success, which is the state where no dump can have run, so Delete Dumps clears it at no cost to the owner and no separate reset action is needed.

Keying the log on `get_serial()` was considered and rejected: `panda/python/__init__.py:620-622` documents it as the comma-issued dongle id, so it identifies the comma and would pool attempts across every car that device touches, letting a comma arrive at a fresh car already blocked.

### Where the gate lives

`is_unlock_blocked()` runs inside `extractor.security_access_with_log()`, between the seed and the send, and all three unlock paths call that one function. Disabling rows in `index.html` stops a tap and nothing else: a direct POST, a stale page already open on a phone, and the two unlock paths outside the six range rows all reach `SEND_KEY` on their own. A test asserts the call list on a blocked ECU reads `[REQUEST_SEED]` alone.

That one function catches **all five** exceptions `security_access()` can raise, where the three original call sites caught three. `InvalidSubFunctionError` (`uds.py:261`, raised at `:673` while parsing a response) fires after the key is on the wire, so leaving it uncaught reached an unlock with no log entry. `InvalidSubAddressError` (`:265`, raised at `:382`) cannot fire here — that raise sits under `if self.rx_sub_addr is not None:` and every TSKM `UdsClient` passes four positional arguments, leaving it `None` — and is caught anyway so the set matches what the callee declares.

### Seven defects the passes caught

All were live in an earlier cut and all are fixed. The last three came from a review Calvin relayed on 2026-08-19, each reproduced in the tree before being taken:

1. `has_run` and `blocked` were computed only at job end, so a range dump that got a rejected key would leave the index rows enabled until a restart. They are now recomputed on every `/api/preflight-status` poll.
2. Setting the harness label saved it but did not re-render the screenshot block, so the artifact an owner sends said "not stated" for a pin state they had stated.
3. `shutil.rmtree` and an `rglob` walker sat in `server.py`, against the Hard Rule that the server is HTTP routing only. Both moved to `tsk/lib/dump_files.py`.
4. The first `.hidden-row` rule lost to `.group-item { display: block }` at `index.html:162`, since both were specificity 0-1-0 and the `.group-item` rule came later. The selector is now `.hidden-row, .group-item.hidden-row`.
5. **`list_reports()` ordered on the whole filename, so the serial outranked the stamp.** `preflight_unattributed_*` leads with `u` (117) and a Toyota serial with `8` (56), so one unattributed report stayed "latest" forever and `rehydrate_preflight_state()` fed that older failed run into the page after every restart. It now sorts on `report_stamp()`, which right-splits the name because `report_path()` keeps `_` in its sanitiser and a serial carrying one would break a left-split. A name with no 15-character stamp sorts last rather than raising, which covers the `"unknown"` stamp `save_report()` writes.
6. **`delete_dumps()` returned one bool for two causes**, and `/api/delete-dumps` mapped it to "A panda operation is in progress", so a permission failure told the owner to wait for something already finished. It returns a reason token now: `"busy"` keeps the 409, `"failed"` gets a 500 naming the real problem, `""` is success.

### Revision, 2026-08-20, after the first in-car run

Span ran preflight on his 2025 Corolla Hybrid on 2026-08-19, the first time it ever ran in a car. It worked as designed and exposed four defects, all fixed above. His run also produced the first `param=1` measurement on any car: the EPS answered a DEFAULT session on bus 1 under **both** params, on a panda reporting `harness flipped`, with `app_sw_id 8965F12080008A3111213000` and `ecu_serial 8965012N50E12H030731`. 1. **The exploit ran through the OBD-II gateway.** `_choose_route()` returned the first answering entry in sweep order and the sweep is `for param in (0, 1): for bus in (0, 1, 2)`, so `(1, 0)` beat `(1, 1)` on ordering alone. `param == 0` is `CAN_MODE_OBD_CAN2` (`panda/board/main.c:73-76`) and `opendbc_repo/opendbc/safety/modes/elm327.h:35` says that multiplexes bus 1 to the OBD-II port. The dual sweep measured that `param=1` works and the tool ignored it. Replaced by the route probe.
2. **The dump rows unlocked on `has_run`.** A route is stored before the exploit, so his run stored `(1, 0)`, died at PROGRAMMING, and left all six range rows plus the extractor and DataFlash rows live. He then spent the session running five profile pages that failed identically to what the report had already printed. The gate is now `passed`, which is `result == "ready to dump"`, and it covers the extractor and DataFlash rows too, since both run the session ladder. The owner how-to already promised this behaviour: "The dump buttons stay locked until it passes." The doc was right and the code was not.
3. **`Detected` named the wrong thing.** See the Route section: `car_harness_status` reads plug orientation from two ADC pins and cannot see a repin, and Span's stock-pinned car showed `Detected` under **Swapped**. Asking him to tap Swapped and re-run could not change anything, since the label fed nothing, so that second set of runs was a guaranteed repeat. The whole surface is deleted.
4. **`CLAUDE.md` said the owner protocol spans 3 car restarts.** The doc has drive cycles at steps 10, 14, 20 and 26, and its own step 1 says 4. The dump counts in the Reference entry were right.

**Three more defects, in the new code, caught before it shipped.** All three were found by the route-probe suite and its positive controls rather than by reading:

5. `_probe_lines()` suppressed the liveness line by comparing against a literal `"answered"` that `_probe_route()` never writes, so every healthy route printed two extra lines on a phone screen for no information. The guard is now `EXPECTED_LIVENESS`.
6. `render_screenshot()` derived the `Steering ECU` line from `route`, which after this change means "the route that opened PROGRAMMING". A car whose ECU answered perfectly and then stopped at PROGRAMMING, which is Span's car exactly, was reported as `no answer on any bus`. It reads off the sweep now.
7. `rehydrate_preflight_state()` called `_refresh_preflight_gates()` before loading the report, so a restart computed the gate from an empty report and briefly locked the rows on a car that had already passed. The refresh moved after the load.

**What one press now measures.** Every answering route gets the ladder and the four services, so a run that opens PROGRAMMING nowhere still ships the cross-route comparison that settles Corolla open item 0: PROGRAMMING opening on `param=1` means dumps come off that car and half the `span` record is gateway artifacts; the four services answering on `param=1` while silent on `param=0` means the gateway was dropping them and the wall is PROGRAMMING alone; all of it silent on both means the 07-25 reading survives, the software path on that car is finished, and the repin is the answer, with albinoelephant's 15 dumps on the same `8965F12` family as precedent.

**Standing rule from 07-25 — "test everything" means the full value space.** Everything is the complete enumeration — every service 0x00–0xFF, every sub-function 0x00–0xFF, every DID 0x0000–0xFFFF — not the subset that is standard, documented, meaningful, or safe. Safety constrains *how* a value is sent, never *whether* it is sent: ask in a form that must be rejected (bare service byte, nonexistent DID, out-of-range address, invalid sub-function) and the ECU answers without acting, because it decides whether to respond before it decides whether to act. Runtime is a scheduling problem, not a scoping one — if full coverage takes hours, build a resumable deadline-bounded job, not a shorter list. Any value not sent must appear in the output as an explicit reasoned omission; a shorter list is never the silent answer. The failure mode this replaces: designing every probe to fit a one-tap sixty-second page, which forces curation and then rationalises the subset as "the meaningful ones."
